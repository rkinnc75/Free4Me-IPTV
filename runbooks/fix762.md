# fix762 — Stall watchdog: EOF fast path for provider-dropped live streams

Release: **v4.1.63+762** · Base: **v4.1.62+761 (main @ aff7d7b)** · Tag: **v4.1.63**

## What this fixes

Field evidence — S938U log, 2026-07-27, `US| YES NETWORK HD`. The provider closed the `.ts` connection three times in four minutes. Every drop read identically:

```
22:54:09  cache-speed -> 0          (server stops sending)
          cache drains 20s -> 0 linearly, playback continues
22:54:27  eof-reached=yes, core-idle=yes, position frozen at 52s
22:54:42  fix753 watchdog fires after its full 15 s window -> reconnect
22:54:45  playing again
```

So each drop cost **~15 s of frozen picture** on top of the unavoidable ~2 s reopen — and mpv had already published `eof-reached=yes` at 22:54:27. The watchdog was waiting out a timer for information it already had.

This adds a second, shorter window to the same watchdog: when a **livestream's** position has been frozen for one full 3 s sample interval **and** `cache-speed == 0` **and** `eof-reached == yes`, reconnect immediately. Measured effect: ~15 s of dead screen per drop becomes ~3–6 s.

**Note on the stutter this log was captured for: it is NOT in this fix, and not in the app.** The perceived judder was `devCapFpsLowRam=true` forcing `vf=lavfi=[fps=fps=30]` on a 59.94 fps source (that flag lost its low-RAM gate in fix624 and now applies to every device). That is a settings change, delivered separately as a tuned backup — no code change. The reconnect loop itself is the provider dropping the connection; nothing app-side can prevent it, only recover faster.

## Why an EOF check is safe where fix753's rejected discriminators were not

fix753 tested and falsified five candidate wedge discriminators — `cacheSpeed==0`, cache depth, `core-idle`, mpv `pause`, and `demuxer-cache-time` progress — because a settled user pause is sensor-identical to a wedge on all of them.

`eof-reached` is different in kind: **pausing does not make the demuxer reach end-of-stream.** It is a statement about the read side being finished, which on a live feed only happens when the server closed the connection. Verified against the field log: 44 `eof=yes` samples, every one inside a provider drop, **none** in the clean 26-minute session that preceded them.

Guard rails kept deliberately tight, all pinned by tests:

- **Livestream only.** VOD legitimately reaches EOF when a movie ends; firing there would reconnect the user into a finished film. (`onDisconnect` has its own livestream guard too — defence in depth.)
- **EOF confirms, never replaces.** `cacheSpeed == 0` remains a precondition for *both* windows.
- **A null read is non-confirming**, same contract as `readCacheSpeed` — on missing data the fast path falls through to the unchanged 15 s window rather than firing.
- **Single-property read**, not `readPlaybackStats()` — that poll only runs while debug logging is on, and a watchdog that only works with debug logging enabled is exactly the fix753 trap.
- **The full 15 s window is behaviourally untouched**, and only pays the extra property read on the fast path.
- **The reconnect reason literal stays `'stall watchdog'`.** It is log-only (nothing branches on it), fix747's suite pins it, and the rolling log analyzer keys on it. The fast path is already distinguishable from the `AppLog.warn` line, so forking the value would buy nothing and break a shipped test.
